# 0x0000 — What `dev-store` is for

**Status:** reference, not an issue
**Date:** 2026-09-17
**Branch:** `dev-store`

## The goal

`letloop store` is a content-addressed source package manager built into
letloop. The branch exists to make one claim true end to end:

> letloop builds static binaries from Scheme and C, on any Linux host,
> depending on nothing the host distribution provides.

"Source package manager" is the C half of that. Scheme is not packaged and
is not meant to be: letloop ships its own libraries, and everything else a
user writes is plain source files on the library path. What a user cannot
supply as source is a C library, because a C library has to be built, and
building it needs a compiler, a rootfs and a reproducible recipe. That
recipe is a derivation, and the store is what runs it.

So the division of labour is:

| what | who supplies it | as |
| --- | --- | --- |
| letloop's own Scheme libraries | letloop | shipped in the release prefix |
| the user's Scheme | the user | source files, named on the command line |
| the user's C | the user | a store specification, a derivation |
| the C letloop itself needs | letloop | packages under `src/letloop/package/` |

## How the pieces fit

A derivation names a rootfs, some hash-pinned fetches, a build script and
an output directory. The script runs under `bwrap` with the network off,
the output is hashed with BLAKE3, and it lands at `<name>-<hash>`. Two
derivations producing identical bytes collapse to one path.

A package is an ordinary Scheme library exporting `package`, so package
definitions ship inside a release the way any other library does, and a
project's own packages sit beside it. `letloop store build NAME` resolves
`(package NAME)` first and `(letloop package NAME)` second, so a user's
package shadows a shipped one by name.

Linking is inferred rather than declared. A binding library says it has C
behind it with `define-shared-object`; `letloop compile` walks the import
closure, maps each such library to a package name longest-part first, and
links whatever archives the store already holds. It never builds. Builds
happen only where they were asked for, at `letloop store build`.

The bootstrap chain in `checks/letloop/bootstrap.scm` is the proof: from
two hash-pinned prebuilt binaries, a musl toolchain and a BusyBox, it
builds a rootfs, a shell, make, the FFI libraries, ChezScheme and letloop
itself, then gates the result by compiling and running programs with it
from outside the store. It runs under upstream Chez, with no letloop
involved, because requiring a letloop to produce the first letloop was the
circularity the branch set out to break.

## What a release is

The chain's `letloop` output, unpacked anywhere, with the store inside the
prefix at `lib/letloop/store`. The binary finds its boot files, its
libraries and its store by walking up from `/proc/self/exe`, so no
environment variable is needed and the tree can be moved. Shipping the C
package outputs inside that store is what lets a user link statically
without ever running a sandbox; substitution is an optimisation on top,
never a requirement.

## Verified on this branch

A user project holding a derivation for a C library, a binding library
using `define-shared-object`, and a program importing it, builds and links
with no letloop checkout present:

```
letloop store build /tmp/user-project arith
letloop compile   /tmp/user-project app.scm main
./a.out                 # 42, and needs no libarith at run time
```

The issues numbered from `0x0001` are what stands between that and the
claim at the top of this file being true without qualification.
