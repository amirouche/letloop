# 0x0000 — What `dev-store` is for

**Status:** specification, not an issue
**Date:** 2026-09-17 (rewritten after the scope review of the same day)
**Branch:** `dev-store`

## The goal, as a test

A user downloads one letloop release tarball onto a Linux machine that
has no C compiler, no development headers and no package installed for
letloop's sake. They unpack it somewhere they own. They write a Scheme
program, a binding library, and a derivation for a C library the
program needs. Then:

```
letloop store build arith
letloop compile app.scm main
./a.out
```

The result is one file. It runs on any x86_64 Linux, whatever its libc,
from an empty directory, with nothing beside it and no environment
variable set. `file` reports it statically linked; `readelf -l` shows
no `INTERP` segment. Nothing the host distribution provides took part
in producing it, with the two exceptions listed under *What the host
must provide*.

That paragraph is the whole claim. Everything else in this file is a
consequence of it or a decision about how to make it true.

## Scope

**In scope**

- Static x86_64-linux-musl executables from Scheme programs that import
  binding libraries with C archives behind them.
- C libraries only. A user supplies one as a derivation; letloop
  supplies the ones its own bindings need as packages under
  `src/letloop/package/`.
- Producing the release itself with the same machinery, from two
  hash-pinned prebuilt binaries, under upstream Chez.

**Non-goals, decided rather than deferred**

- **C++.** No library motivates it. The link line links C, and no
  package field describes `-lstdc++` or libatomic. Revisit when a real
  library asks.
- **`letloop desktop` and anything that dlopens.** Under static musl
  `dlopen` does not work, and Vulkan loads its drivers that way. The
  desktop stays a dynamic, host-libc program and is outside this claim.
  So is a program that resolves bindings at run time through
  `--visible-libraries` and `eval`.
- **Any architecture but x86_64.** No cross-compilation. The store path
  carries the system name from now on so that adding one later moves no
  existing output.
- **Multi-user or system-wide installs.** The store lives inside the
  release prefix and is written in place. The rule is: unpack it
  somewhere you own. No daemon, no setuid helper, no shared store.
- **Scheme packaging.** letloop ships its libraries in the prefix; the
  user's Scheme is source on the library path.
- **Building a compiler from source.** The musl toolchain is trusted
  on its hash, Nix's bargain, taken deliberately.
- **`letloop update`.** Releases will be hosted on letloop.cloud. Until
  that exists a release is a tarball built by the maintainer, and
  nothing in this branch may depend on the host being up.

## Decisions

Each one answers a place where the branch, as first built, contradicted
the goal. The issue that recorded the contradiction is named where one
exists.

1. **`letloop compile` may download.** Linking needs a linker, an
   assembler, `nm`, musl's crt files and `libc.a`. None of that is in a
   release, and the host's compiler is the wrong one: it links against
   the host libc, which is issue `0x0001`. So on first use compile
   fetches the pinned musl toolchain through the store, exactly the
   fetch-only `toolchain` package the bootstrap chain already trusts,
   and links with it. The host's `cc` is never consulted. There is no
   glibc mode. Issue `0x0006`.
2. **Fetches carry a list of URLs.** Upstream musl.cc first, the
   letloop.cloud mirror when it exists, tried in order, every byte
   hash-checked regardless of origin. Adding the mirror is a one-line
   change in a package file, not a code change. Issue `0x000A`.
3. **The sandbox ships with the release.** `bwrap` is built statically
   in the chain and installed beside the binary, so `letloop store
   build` needs no host `bwrap`. Unprivileged user namespaces remain a
   host requirement; letloop reports their absence as one sentence
   naming the sysctl, and does not attempt to build without them.
   Issue `0x000B`.
4. **A binding names its package.** `define-shared-object` takes an
   explicit package name. Inference from the library name is gone,
   together with the rule that only libraries declaring a shared object
   are consulted. A binding with no package declaration links nothing
   and says so; a package name that resolves to no library is a compile
   error, not a note. Issue `0x0007`; it retires the naming rule in
   `0x0005`.
5. **Compile resolves the derivation, not the name.** For each declared
   package, compile loads the package library, resolves its inputs
   through the store's index, computes the same key `store build`
   would, and looks up that key. A miss is "not built", reported with
   the command that builds it, and compile exits nonzero. There is no
   dlopen fallback: issue `0x0002`. Two outputs sharing a name no longer
   break anything, since nothing looks up by name: half of `0x0004`.
   Issue `0x0008`.
6. **The index is a source of truth.** What is `.cache` today becomes
   the store's index: key to output path. Removing an index entry is
   how a path becomes unreachable, and garbage collection deletes what
   no index entry names. That is the other half of `0x0004`.
7. **The installed package directory is on every path.**
   `$PREFIX/lib/letloop/package/` is where a user installs a package by
   name, and both `store build` and `compile` see it. Issue `0x0003`.
8. **Symbol conflicts are errors.** Before linking, compile reads the
   defined global symbols of every archive it is about to link and
   refuses if two archives define one, naming both and the symbol. Link
   order never decides. libsodium and libargon2 both define
   `argon2id_hash_raw`; the resolution is that `(letloop argon2)` names
   the `sodium` package, since libsodium vendors argon2, not that the
   linker picks one. Issue `0x0009`.
9. **Store paths carry the system.** `<store>/x86_64-linux-musl/<name>-<hash>`.
   Fetch-only outputs are placed there too; a toolchain tarball is as
   system-specific as anything built with it. Issue `0x000A`.
10. **A release is the chain's `letloop` output, with the store
    inside.** Unpacked anywhere, moved freely, found by walking up from
    `/proc/self/exe`. It ships the built outputs of every package
    letloop's own bindings name, so a user linking only those never runs
    a sandbox and never downloads more than the toolchain.

## What the host must provide

Exactly these, and each is checked at the point of use with a message
that names it:

| for | needs from the host |
| --- | --- |
| running a compiled program | a Linux kernel of the same architecture |
| `letloop compile` | network, once, for the toolchain fetch |
| `letloop store build` | network for fetches; unprivileged user namespaces for the sandbox |
| producing a release | upstream Chez, `curl`, and the gates' inspection tools, per the store README |

## How the pieces fit

A derivation names a rootfs, hash-pinned fetches, a build script and an
output directory. The script runs under `bwrap` with the network off,
the output is hashed with BLAKE3, and it lands at
`<system>/<name>-<hash>`. Two derivations producing identical bytes
collapse to one path; the index records which key produced it.

A package is an ordinary Scheme library exporting `package`, so package
definitions ship inside a release like any other library, and a
project's own sit beside it in `lib/letloop/package/`. `letloop store
build NAME` resolves `(package NAME)` first and `(letloop package NAME)`
second, so a user's package shadows a shipped one.

A binding library declares its shared object and its package. `letloop
compile` walks the import closure, collects the declared packages,
resolves each through the index, and links the archives it finds, plus
the closure each package's own `inputs` give it, inside
`-Wl,--start-group`. It builds nothing. Builds happen only at `letloop
store build`.

The bootstrap chain in `checks/letloop/bootstrap.scm` produces the
release: from the pinned toolchain and BusyBox it builds a rootfs, a
shell, make, `bwrap`, the FFI libraries, ChezScheme and letloop, then
gates the result from outside the store. It runs under upstream Chez,
because requiring a letloop to produce the first letloop was the
circularity the branch set out to break.

## Claims and their gates

A claim with no gate is not a claim. Each row names the check that
fails when only that claim is broken.

| must be able to | gated by |
| --- | --- |
| Compile and run the acceptance test from a release tarball, in a container with no `cc`, no headers, no `bwrap` | `checks/release.sh`, to be written; the one gate for the whole claim |
| Produce an executable with no `INTERP` segment on a glibc host | `checks/release.sh`, `readelf -l` on `a.out` |
| Fetch the toolchain on first compile, from the first reachable URL of a list | `~check-store-*/fetch-mirrors`, to be written |
| Refuse to compile when a declared package is unbuilt, with exit status nonzero | `checks/compile-unbuilt.sh`, to be written |
| Refuse to link two archives defining one symbol, naming both | `checks/compile-conflict.sh`, to be written |
| Resolve a package to the exact output its derivation would produce today, by key | `~check-store-*/index-lookup`, to be written |
| Delete every store path no index entry names, and nothing else | `~check-store-*/gc`, to be written |
| Build a user's package from `lib/letloop/package/` by bare name, then link it by the same name | the `/tmp/user-project` scenario in *Verified*, installed rather than passed as a directory |
| Build under the shipped static `bwrap` with the host's absent | `bootstrap.scm`, self-hosting gate, with `bwrap` masked from `$PATH` |
| Everything the store README already gates | unchanged |

## Verified on this branch

A user project holding a derivation for a C library, a binding library
using `define-shared-object`, and a program importing it, builds and
links with no letloop checkout present:

```
letloop store build /tmp/user-project arith
letloop compile   /tmp/user-project app.scm main
./a.out                 # 42, and needs no libarith at run time
```

Still true and still short of the claim: the executable that run
produced was linked by the host's glibc compiler, and the directory had
to be passed twice. The issues numbered from `0x0001` are what stands
between that and the acceptance test at the top of this file. The
decisions above say which way each is to be closed, and `0x0006` to
`0x000B` file the work the decisions themselves create.
