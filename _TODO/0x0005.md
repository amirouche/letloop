# 0x0005 — The package interface is undocumented

**Status:** open
**Severity:** medium, the feature exists and nobody can find it
**Area:** documentation

## Problem

Everything a user needs in order to package a C library for their own
program works, and none of it is written down anywhere a user would look.
Three things in particular exist only as source comments:

1. **The derivation grammar.** The full shape, including which clauses are
   optional and which combinations are rejected, lives in a header comment
   in `src/letloop/store/derivation.body.scm`.
2. **The naming rule that drives linking.** A library named `(arith)` asks
   the store for a package named `(package arith)`. A deeper name tries
   its parts longest first, so `(mycorp net zlib)` asks for
   `(package mycorp net zlib)`, then `(package mycorp net)`, then
   `(package mycorp)`. This is the entire interface between a user's
   Scheme and a user's C, and it appears only in a comment on
   `library-package-components`.
3. **The requirement that a binding library declare `define-shared-object`.**
   Inference deliberately consults no other library, so a binding written
   without it is never linked and never diagnosed. The reason is good, it
   is what stops a fixture package from being built by a bare name match,
   but the consequence is invisible from outside.

`src/letloop/store/README.md` documents the store as a subsystem: how
derivations resolve, how the bootstrap chain is laid out, what is
deliberately absent. It is written for someone working on the store, not
for someone using it.

## Why it matters

The workflow verified on this branch is four files and two commands, and a
user cannot discover any of it. Without the naming rule they cannot make
linking happen at all, and the failure mode is silent: the program builds
and then dies on first use with a dlopen error naming a shared object they
never intended to have.

## Fix

A user-facing document, `letloop store` as a thing to use rather than a
thing to read. Minimum contents:

- The worked example end to end. A C library, a derivation for it, a
  binding library, a program, the two commands, the result.
- How a binding names its package. Decision 4 in `0x0000` replaces the
  longest-first naming rule with an explicit declaration, filed as
  `0x0007`; document the declaration, not the rule.
- The derivation grammar as a reference, lifted out of the comment.
- Where packages live: the project directory, and the installed directory
  at `$LETLOOP_PREFIX/lib/letloop/package/`, noting the asymmetry in
  `0x0003` until that is fixed.
- What the store does not do: no version solving, no Scheme packaging, no
  automatic building during a compile.

`src/letloop-usage.md` should gain a line pointing at it, since that is
what `letloop help` prints.

## Note

Write this after `0x0001`, `0x0003` and `0x0007`, not before. Both change what the
document would have to say, and documenting the current asymmetry in
detail only to delete it a week later is wasted work. `0x0002` changes a
failure message, which the document should quote once it is correct.
