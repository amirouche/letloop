# 0x0006 — `letloop compile` links with the host compiler instead of the store's toolchain

**Status:** open
**Severity:** high, it is the mechanism behind `0x0001`
**Area:** `letloop compile`, `(letloop package toolchain)`, `(letloop store)`

## Problem

`c-compiler` in `src/letloop/base.scm` looks up `$CC`, `cc`, `gcc`. A
release does not ship a compiler, so a user without one cannot link at
all, and a user with one gets the host libc (`0x0001`). Decision 1 in
`0x0000`: compile fetches the pinned musl toolchain through the store on
first use and links with it, unconditionally `-static`. The host's
compiler is never consulted.

## What is missing

1. A fetch-and-extract derivation shape. The `toolchain` package is
   fetch-only and its tarball is never unpacked outside a sandboxed
   rootfs build; compile must not need `bwrap`. Extraction needs `tar`
   and nothing else, and the extracted tree is what lands in the store.
2. `c-compiler` resolves `(letloop package toolchain)` through the
   store, triggering the fetch when absent, and returns the `gcc` inside
   it. `nm`, `ld` and `as` come from the same tree.
3. Drop the triple test; `-static` always.

## Gate

`checks/release.sh`: in a container with no `cc` on `$PATH`, the
acceptance test in `0x0000` produces an executable with no `INTERP`
segment.
