# 0x0004 — The store has no garbage collection

**Status:** open
**Severity:** medium, unbounded growth with no way to reclaim
**Area:** `letloop store`

## Problem

Nothing removes anything from the store. Every build that produces new
bytes leaves a new `<name>-<hash>` directory, and the previous one stays
for as long as the filesystem holds out. There is no command to list what
is unreachable, no notion of a root, and no way to delete a path safely.

## Evidence

The bootstrap chain's own store, after the runs on this branch:

| store after the chain | 1.7 GB |
| --- | --- |

It already holds two outputs each for four packages, because those
derivations changed during the work. Separately, editing one line of C in
a user's own package and rebuilding added a second copy of it immediately.

## Why it matters

Two different costs. The obvious one is disk, sharpened by the store
living inside the release prefix now, so it grows where the installation
is rather than somewhere a user thinks of as a cache.

The subtler one is that duplicate outputs actively break linking. Lookup
by name returns nothing when more than one path matches, because it cannot
tell which is current without resolving the derivation, so the package is
reported as unbuilt and the program falls back to dlopen. Growth is not
merely untidy here, it is the mechanism by which a working build stops
working. See `0x0002`.

## Fix

The pieces, smallest first:

1. **Promote `.cache` to the store's index**, key to output path, and a
   source of truth rather than a cache (decision 6 in `0x0000`). Lookup
   by key is what fixes the duplicate-output failure above, filed as
   `0x0008`, and an index entry is the natural root for anything that
   follows.
2. **Roots.** A path is live if something points at it: the pointer above,
   a compiled program's recorded inputs, or an explicit root a user asked
   for.
3. **A reachability walk.** A derivation's inputs are already resolved
   depth-first during a build, so the graph exists; what is missing is
   recording it beside the output rather than discarding it.
4. **A delete command**, with a dry run that lists what would go.

Nix's shape is the obvious model and the store already borrows most of it.
The one deliberate difference to preserve is that this store is addressed
by output content, not by a statically computable derivation hash, which
means reachability has to be recorded at build time rather than recomputed
later. The same property is what stops a substituter from being asked
whether it holds a given derivation's output without building that
derivation's inputs first; a separate design question, not yet filed.
