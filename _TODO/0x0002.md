# 0x0002 — Compiling falls back to dlopen instead of refusing

**Status:** open
**Severity:** high, produces a binary that fails at first use
**Area:** `letloop compile`, `infer-archives!`

## Problem

When a library in the import closure declares a shared object and no
archive can be found for it, `letloop compile` prints a note and carries
on, emitting a program that will `dlopen` at run time:

```
* (arith) has a package that is not built; it will dlopen at run time.
** Build it to link it in: letloop store build arith
```

That was a reasonable default when dynamic loading was the normal case.
It is the wrong default for a tool whose output is meant to be static: the
failure moves from compile time, where it is one line of diagnostic, to
run time, where it is an exception in a deployed binary.

## Evidence

A user's own C package, built, then rebuilt after an edit that changed its
output. The compile after the rebuild printed the note above and produced
a binary that fails on first call:

```
$ ./a.out
Exception in libarith: cannot dlopen shared object, tried with irritant "libarith.so"
```

Nothing in the compile exited nonzero.

## Why it matters

Two ways it hurts. A program that was static yesterday can become dynamic
today without the build failing, so nothing catches the regression except
running it. And the shared object it looks for does not exist anywhere on
a machine where the library was only ever built as an archive, so the
fallback is not a graceful degradation, it is a deferred crash.

## Fix

Fail the compile. Report the library, the package name it resolved to, and
the command that would build it, then exit nonzero.

An escape hatch may be wanted for the genuinely dynamic case, for example
a program that wants the host's own libvulkan, which is a loader that
dlopens drivers itself and has no archive to link. If so, make it an
explicit flag rather than the default, so that choosing dynamic is a
decision someone typed rather than one that happened.

## Related

The concrete trigger in the evidence above is the duplicate-output bug:
after a package is built twice with different outputs, the lookup by name
refuses to choose between the two store paths and reports the package as
unbuilt, which is false. That is a separate defect with a separate fix: `letloop compile`
resolves a package through the store's index by derivation key rather
than by name, per decision 5 in `0x0000`. Filed as `0x0008`.
