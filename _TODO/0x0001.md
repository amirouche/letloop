# 0x0001 — Static is not guaranteed, it is inherited from the host compiler

**Status:** open
**Severity:** high, it falsifies the branch's central claim
**Area:** `letloop compile`, `(letloop package toolchain)`

## Problem

`letloop compile` links a program's C archives by re-compiling
`letloop-main.c` against `kernel.o` with whatever compiler is on the host.
It passes `-static` only when that compiler's triple mentions musl:

```scheme
(static-flag (if (string-contains? "musl" triple) "-static" ""))
```

On a glibc host the archives are still linked statically, but the
executable is not: it requests the glibc dynamic loader, and carries all
of glibc's usual runtime assumptions with it. "letloop produces static
binaries" is therefore a property of whoever compiled, not a promise the
tool makes.

## Evidence

A program importing `(letloop www)`, compiled on this host against the
bootstrap store's `tls`, then inspected:

```
$ file probe
ELF 64-bit LSB pie executable, x86-64, dynamically linked,
  interpreter /lib64/ld-linux-x86-64.so.2

$ ldd probe | grep -Ei 'tls|ssl|crypto'
(nothing)
```

So libtls, libssl and libcrypto are in the binary and glibc is not. The
same holds for a user's own C package: the archive is linked, the loader
is still required.

## Why it matters

Every downstream promise rests on this one. A relocatable binary that
needs a loader is not relocatable across distributions, which is the
reason the bootstrap chain builds against musl in the first place. It also
makes the chain's own gates stronger than what a user gets: the chain
asserts no INTERP segment on everything it produces, because it builds
inside a musl rootfs, while the same `letloop compile` on a user's machine
quietly produces something weaker.

## Fix

Take the compiler from the store rather than from `$PATH`, and pass
`-static` unconditionally.

The toolchain is already a package, and it is fetch-only: no rootfs, no
script, no sandbox. An operator therefore needs only a download to get a
musl compiler, which keeps `bwrap` off the ordinary path entirely.

What blocks it today is that the fetched tarball is never unpacked:

```scheme
;; Nothing is unpacked here; the tarball lands in the store as-is.
;; bootstrap-rootfs.derivation.scm untars it, having a real `tar` to do it with.
```

Only a sandboxed rootfs build extracts it, which would put `bwrap` back in
the path. The missing piece is a fetch-and-extract derivation shape, which
needs `curl` and `tar` and nothing else, after which `letloop compile` can
resolve the toolchain by package name the way it already resolves
archives.

Order of work: the extract shape first, then the compiler lookup, then
drop the triple test.
