HTTP Server Benchmark: buffer-based vs byte-generator HTTP parser
=================================================================

Date: 2026-03-18
Tool: wrk -t4 -c64 -d10s http://127.0.0.1:PORT/
Build: --optimize-level=3 --disable-garbage-collector
Instrumentation: pk silenced (no I/O per connection)
Workload: "Hello, World!" response, keep-alive, epoll event loop
Platform: Linux 6.17.0-19-generic, Chez Scheme 10.3.0

OLD = byte-generator parser (http-read-bytes unbuffers chunks into per-byte thunk)
NEW = buffer-based parser (make-reader with read-byte!/read-bytes! over chunk boundaries)

--- Raw results ---

OLD round 1:  11,169 req/s  avg 4.56ms  max  987ms  stdev 39.22ms  timeouts 21
OLD round 2:  11,147 req/s  avg 1.46ms  max  109ms  stdev  1.63ms  timeouts 25
OLD round 3:  11,414 req/s  avg 7.45ms  max 1640ms  stdev 73.19ms  timeouts 23

NEW round 1:  11,546 req/s  avg 3.63ms  max 1040ms  stdev 36.86ms  timeouts 22
NEW round 2:  11,251 req/s  avg 1.49ms  max  147ms  stdev  2.54ms  timeouts 15
NEW round 3:  11,425 req/s  avg 16.0ms  max 1990ms  stdev 130.0ms  timeouts 13

--- Summary (3-run average) ---

                  OLD           NEW          delta
req/s:          11,243        11,407          +1.5%
avg latency:     4.49ms        7.04ms        (high variance, dominated by outliers)
max latency:      912ms       1059ms         (high variance)
timeouts:          23           17           -26%

--- Analysis ---

Throughput is bottlenecked by the single-threaded epoll event loop and
socket syscalls, not by the HTTP parser. Both versions saturate at ~11.3k
req/s under this workload.

The buffer-based parser eliminates:
  - per-byte function call overhead (http-read-bytes thunk)
  - per-byte cons allocation in http-line-read
  - the http-read-bytes adapter layer in http-serve.scm

The write side now:
  - writes headers in a single accumulator call (eliminates Nagle stalls)
  - both request-write and response-write accept body as generator (symmetric API)

Timeout count improved (~26% fewer), suggesting fewer stalls from delayed-ACK
interaction with the old two-call response write pattern.

The real gains from this rework are architectural (symmetric API, streaming
body support, no adapter layer) rather than throughput. To see throughput
improvements, the event loop itself would need to be the focus (multi-threaded
accept, io_uring, etc).
